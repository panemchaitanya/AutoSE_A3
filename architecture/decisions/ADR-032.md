# ADR-032: Column-count checks for A1 tables (extends ADR-029)

Status: proposed (post-disclosure, after runs 21 to 24). Merge only between runs.

## Context
Runs 21, 23 and 24 (#39) failed requirements on broken table separators. Question asked:
is the write path truncating rows, or is the model producing them? Evidence from run 24
(artifact 14989379895): the Developer-visible raw model reply in
transcript_requirements_attempt1_*.json is complete valid JSON and already contains
`|---|---|---| p` verbatim; `_tool_write_file` writes the received `content` unchanged
(no slicing). So the defect is model generation, not file or transport truncation.
In the correction pass the model replaced the junk with a fourth dash cell, giving a
4-cell separator under a 3-cell header (runs 23 and 24 final files). The ADR-029 check does
not see that, so the judge reported it vaguely.

## Decision
Extend `a1_checks.table_format_errors`: within each table the separator row must be a row
of dash cells with the same cell count as the header, and every data row must have the
same cell count. Messages give document, line, found and expected counts. Escaped pipes
(`\|`) do not split cells. No auto-repair: the correction attempt receives the exact
message. This only adds checks; no check, judge or limit is loosened.

## Validation
Scanned the bundles of runs 17 to 24 (including the passed run 22 bundle): zero errors on
all bundles that had no table defect; the run 21, 23 and 24 defects are reported with line
numbers. Tests in `test_a1_checks.py`.

## Consequences
Cheaper, exact correction feedback for one frequent defect class. Not a pass claim.
