# ADR-025: Record each edit's outcome in the durable action ledger

## Status

Accepted, 25 November 2026, 03:40 IST, late work. Extends ADR-017 and the action
ledger. Nothing superseded. Step cap (40), token budget, checks and models are
unchanged.

## Context

Run 45490367204 (#37) passed Stage 1 and Stage 2, then the Developer failed with
"step cap 40 reached" (develop job, 21:58:46Z to 22:02:20Z). Its transcript
(artifact autose-issue-37-develop, transcript_implementation.json) shows the same
edit_file on tinydb/database.py (adding limit to TinyDB.search) sent at steps 8, 12
and 29, interleaved with read_file loops, and no edit to tinydb/table.py, where
Table.search lives. The agent keeps only the last four action pairs, and the ledger
of earlier actions listed only the action and path, not whether an edit worked. After
the first edit succeeded, repeated identical edits fail with "old_text must match
exactly once", which the model cannot interpret without remembering the success.

## Decision

1. The ledger entry of every write_file and edit_file now records its result
   ("applied" or the first 90 characters of the error).
2. When an edit's old_text no longer matches but new_text is present exactly once,
   the observation says the edit was already applied and not to repeat it.

Nothing about what counts as done changes: the Developer still needs a real source
diff, tests and the stage checks.

## Alternatives

- Raise the 40-step cap: a bound change, and it would only lengthen the loop.
- Keep more action pairs in context: costs tokens on every call.

## Consequences

New harness identity from this merge. Effect unproven (one observed failure). Two
unit tests cover the repeated-edit observation, the ledger result and a failed edit.
