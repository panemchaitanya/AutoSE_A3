# ADR-010: Triggers - label or command, owner only, one run per issue

- Status: Superseded by ADR-011 (provider-wide queue)
- Decision area: D10 (Triggers)

## Context

The workflow spends real (if free-tier) quota and opens real PRs, so who can
start it and how often matters as much as what starts it.

## Decision

Two entry points, both from the brief's sketch:

- Adding the label `autose` to an issue (`issues: labeled`).
- Commenting `/autose` on an issue (`issue_comment: created`), plus the
  internal `/autose continue` variant the review workflow posts to feed
  review rounds back into the main workflow.

**Who may start it:** the gate job checks that the actor is the repository
owner (`github.event.sender.login == github.repository_owner`) and exits
neutral otherwise. On my fork that is me; with TAs added as collaborators the
check is the reason their labels cannot accidentally spend my quota.

**Two runs at once:** the workflow sets
`concurrency: { group: autose-${{ github.event.issue.number }} }` with
`cancel-in-progress: false`, so a second trigger on the same issue queues
instead of racing; the gate then sees the first run's `state.json` and
resumes rather than duplicates. Different issues can run in parallel; the
token budget is per issue, and the free-tier rate limit is the real
serialization point (handled by backoff, ADR-006).

## Alternatives considered

- **Any collaborator can trigger.** Rejected for the solo submission: the
  fewer actors, the fewer quota and injection edges; widening the list is a
  one-line change documented here when the project becomes a team repo.
- **Push-to-main as a trigger.** Rejected: the pipeline's unit of work is an
  issue, not a commit; starting on push conflates the two.
- **`cancel-in-progress: true`.** Rejected: cancelling mid-write would leave
  `state.json` and the branch half-updated; queuing keeps the state machine's
  invariant that only one writer advances an issue.

## Consequences

- Starting the system is a deliberately human act (label or comment), which
  matches the story: a maintainer opts an issue into automation.
- All triggers, actors and skips are logged in the gate job's output, so
  "why did nothing happen when I labeled it" is answerable from the run page.
