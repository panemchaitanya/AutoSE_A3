# ADR-033: Quota-aware 429 handling (amends ADR-027)

Status: proposed (post-disclosure, after run 26). Merge only between runs.

## Context
Run 26 (#35, artifact 14991543190): after two flash-lite 429s the harness switched to
gemini-3-flash-preview, whose free daily budget was already spent, and the run ended with
"model retries exhausted" after 18 minutes. The logs did not record whether the first
two 429s were a per-minute burst or the daily cap, so the switch could not be audited.
ADR-027 treats every 429 the same.

## Decision
1. Parse the 429 body for the quota id and provider retry delay (non-secret fields only)
   and record them in calls.jsonl (`quota_id`, `retry_delay_s`). Messages and keys are
   still never logged.
2. A per-minute quota 429 stays on the primary model and waits the provider's delay
   (capped by the existing backoff step, minimum 5 s). Daily or unidentified 429s keep the
   ADR-027 behaviour (switch after 2, 10-minute cooldown).
No retry count, timeout or backoff ceiling changes; no check or judge is loosened.

## Validation
Offline tests in `test_retry_policy.py` (per-minute stays and waits, daily switches,
body parsing) and updated schema assertions in `test_call_log.py`.

## Consequences
Runs after this are a different harness configuration. Not a pass claim.
