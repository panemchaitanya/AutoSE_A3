# ADR-005: Tools - one stdlib agent harness, whitelisted shell, gh only in YAML

- Status: Superseded by ADR-013
- Decision area: D5 (Tools)

## Context

Agents need to read and edit files and run tests. GitHub operations (branch,
push, PR, comments) need to happen too. The question is how each capability
is exposed and how each agent is limited to what it needs.

## Decision

One small agent harness (`workflow/agent/agent.py`, Python stdlib only) used
by every LLM role. It implements a ReAct-style loop: the model replies with a
JSON action, the harness executes it, the result goes back into the
conversation. The tool set is deliberately tiny:

- `read_file`, `list_files` - read-only, inside the repo checkout.
- `write_file` - restricted to the repo tree, and the harness refuses paths
  under `.github/` and `workflow/` so an agent cannot rewrite the workflow
  that runs it.
- `run_shell` - a whitelist: `pytest`, `python`/`python -m`, `grep`, `find`,
  `ls`, `cat`, `head`, `tail`, `git diff|status|show|log`. No `git push`,
  no `git commit`, no `gh`, no `curl`, no network.
- `finish` - returns the stage's structured result JSON.

**All GitHub operations are scripted `gh` CLI calls in workflow YAML steps**,
authenticated by the job's `GITHUB_TOKEN`, never exposed to any agent. Each
job declares only the permissions it needs (`permissions:` per job).

No MCP server: the capability set is small enough that a server adds moving
parts without adding control. The harness's whitelist *is* the permission
model, and it is 30 lines of readable code.

## Alternatives considered

- **GitHub MCP server for repo operations.** Rejected for this design: agents
  would gain issue/PR write capabilities they do not need, and the brief
  warns that tool surface is attack surface. GitHub ops are deterministic
  steps, so they belong in YAML.
- **Full shell access (mini-swe-agent style).** Rejected inside a workflow
  that strangers can trigger with issue text (ADR-009): one convincing
  "run this to debug" instruction in an issue is then a supply-chain hole.
- **A ready-made "fix this issue" action.** Rejected as the core: it would
  blur which decisions were mine. The whole point of the assignment is the
  design around the agents.

## Consequences

- The same harness runs locally for development and in Actions for real runs;
  behavior differences come from inputs, not from two implementations.
- Auditing "what can the agent do" is reading one whitelist.
- New tools are added deliberately, in code, with this ADR amended.
