# ADR-002: Control flow - deterministic state machine across two workflows

- Status: Accepted
- Decision area: D2 (Control flow)

## Context

Someone has to decide when a stage passed, when to go back, and when to stop.
The options are a fixed pipeline (no going back), an LLM orchestrator that
decides the next step, or deterministic code that interprets stage results.

## Decision

A deterministic state machine in `controller.py`. Stages are Actions jobs
chained with `needs:` inside `autose.yml`; each stage ends by updating
`.autose/state.json` on the work branch, and only the controller reads check
results and decides transitions. The implement-test loop (stage 3 <-> 4) runs
inside one job, bounded at 3 cycles. The review loop (stage 6 -> 2 or 3)
crosses workflows: the review runs as a reusable workflow called after
release; when it requests changes it posts a human-readable comment on the PR
*and* re-triggers the main workflow with `gh workflow run` (workflow_dispatch
is exempt from GitHub's rule that GITHUB_TOKEN actions do not trigger new
runs - an ordinary bot comment would silently not re-trigger anything). The
gate job reads `state.json`, applies the requested entry stage, increments
the round counter, and skips completed stages. At most 2 review rounds, then
the run stops for a human.

LLMs produce content and verdicts; **LLMs never choose the next stage.**

## Alternatives considered

- **Fixed linear pipeline.** Rejected: the brief's own table requires going
  back (tests fail -> implementation; reviewer disagrees -> design), so a
  linear pipe would need the loop bolted on anyway.
- **LLM orchestrator with workers.** Rejected for the core loop: routing is
  exactly the part that must be auditable, reproducible and cheap, and an LLM
  router can be talked into skipping a check by a persuasive stage output.
  The controller is ~200 lines anyone can read.
- **One long-running job for everything.** Rejected: the review needs
  different token permissions (ADR-008), and long jobs are fragile against
  runner timeouts and free-tier rate limits; checkpoints between jobs make
  runs resumable.

## Consequences

- Every transition is visible in `state.json` and in the run log: you can
  replay *why* the system went back, not just that it did.
- Budgets (3 fix cycles, 2 review rounds, token cap) are enforced in code,
  not in a prompt, so they cannot be argued with (ADR-009).
- The two-workflow split means the review feedback path is asynchronous and
  visible as PR comments, which is also how a human follows the run.
