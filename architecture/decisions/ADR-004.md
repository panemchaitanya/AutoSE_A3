# ADR-004: State - state.json and artifacts live on the work branch

- Status: Accepted
- Decision area: D4 (State)

## Context

State exists at two lifetimes: within a run (stage N's output feeds stage
N+1) and across runs (a review round two days later must know it is round
two). It also has an audience: the maintainer following along on GitHub.

## Decision

All durable state lives **on the work branch** `autose/issue-N`:

- `.autose/state.json` - stage statuses, fix-cycle count, review rounds,
  cumulative token usage, run IDs. Written only by `controller.py` and the
  workflow steps, never by agents.
- `.autose/artifacts/` - `spec.md`, `design.md`, `diff.patch`,
  `test_report.md`, `pr.md`, `review.md`, committed as they are produced.

Within a run, stages hand off through committed branch files;
`actions/upload-artifact` provides an additional audit copy, not the
inter-job transport. Across runs (review
rounds, restarts), the gate job checks out the branch and reads `state.json`;
an operational `resume` skips stages already marked passed. A fresh
start deliberately creates new state and archives the previous bot tip.

## Alternatives considered

- **Workflow artifacts only.** Rejected as the only store: artifacts expire
  and are awkward to read from another workflow run; the review workflow runs
  days later.
- **PR comments as the state store.** Rejected: comments are a presentation
  layer - fine for human-readable status notes, terrible as a database
  (no schema, editable, noisy).
- **Actions cache.** Rejected: caches are explicitly best-effort and
  evictable; state that decides budgets must be durable.

## Consequences

- The branch is the audit trail: `git log autose/issue-N -- .autose/` replays
  the whole run, which directly serves the brief's "anyone can follow a run".
- A run restarted after a crash (rate limit, runner death) resumes at the
  first non-passed stage; budgets and token counts survive restarts.
- Merge hygiene: `.autose/` is development metadata on a feature branch; a
  maintainer merging the PR can drop it, and the README says so.

## Student discussion, 2026-11-23

Chaitanya chose keeping completed code and retrying testing after an
internet failure instead of discarding and rebuilding good work. This is
his rationale for saving progress. It is not blanket approval of branch
rewrite mechanics or evidence that every interrupted stage is resumable.

## Implementation audit, 2026-11-23

Early failed-stage changes were not committed automatically and required
artifact recovery. Incremental progress files and always-commit development
steps were added later; they are not retroactive evidence. Review results
live in Actions artifacts and posted reviews, not committed state (review
has no contents-write token). Earlier release state stayed pending despite
successful PR creation; that mismatch was fixed for later workflows. State
alone is therefore insufficient for historical stage-rate calculations;
job logs, release checks and posted reviews must be reconciled with it.
