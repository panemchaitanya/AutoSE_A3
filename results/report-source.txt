Repository: https://github.com/panemchaitanya/AutoSE_A3. Comparison fork: AutoSE_A3_Alt. Both derive
from TinyDB pinned at edff96a. The system takes an owner-triggered issue through six fixed stages, leaving the
generated PR unmerged for a person.

Component view
Owner label /autose or authorized dispatch -> deterministic gate + branch state

SpecWriter + read/ledger tools -> checked spec / Designer + repo tools -> plan

Developer + edit/shell tools <-> Tester + pytest / bounded fix cycles

Release + GitHub API -> open PR / fresh Reviewer + read/run only -> verdict

The controller, not a language model, chooses transitions. Five model roles handle analysis and code; release is
scripted. The implementation/testing loop is bounded at three fix cycles and review feedback at two rounds.
Requirements corrections are bounded and exhaustion stops the lineage; roles have 40 steps and a 1.5M-token
lineage cap.

State, tools and information boundaries
Branch .autose/state.json stores stages, counters and events; artifacts retain source documents, transcripts,
call metadata and failures. Actions uploads are additional copies, not the only durable state. Preparation
conversations resume only on a matching fingerprint. Developer/Tester timeout continuations preserve
consumed steps and known usage without replaying prior tool effects.
Roles can read files, list files, write or exact-edit allowed paths, and run whitelisted shell prefixes. Agents cannot
write workflow code or push through their normal tools. These are prototype controls, not a hostile-code
sandbox: arbitrary Python remains possible. The trusted release/gate steps own GitHub mutations.

What was achieved
One corrected A3 feature, search(limit), reached tested release and a posted independent approve-verdict
review. It required disclosed timeout continuations and a mechanical recheck. Other issues stopped or retain
only historical passes. All generated issue PRs remain open. This report records failures rather than converting
them into successes.

Decision 1: deterministic control
A fixed controller exposes exactly which evidence permits a transition. It makes both success and refusal
inspectable: a confident finish cannot overrule a failing pytest exit code. The cost is recovery complexity. The
read-only review job cannot update branch state, so feedback must be collected and routed by a trusted gate
rather than by giving the reviewer push rights.

Decision 2: independent information, not only a new prompt
Asking the same agent to be objective cannot erase its prior reasoning. The reviewer therefore has a fresh
filtered copy and a separate prompt/job. An audit found that assignment README still exposed pipeline
reasoning; ADR016 removed it. Historical verdicts remain labeled boundary-flawed. The later issue 4 review
used the corrected boundary, but shared model-family blind spots and source-comment influence remain.

Decision 3: mechanical checks decide
Compile/import, real source diff, full tests and baseline behavioral contrast are executable claims. The reviewer
and semantic judges are still fallible. Requirements judges can veto untestable criteria or invented readiness,
but cannot manufacture a pass. This correctly exposed inconsistent ledgers, yet also made the
generator/checker contract a dominant failure source.
In an earlier A3 issue 5 attempt, correction was told to fix spec.md while defects lived in the versioned bundle.
The later correction explicitly named all four documents and passed original issue/skill definitions to the judge.
That material change did not erase exhausted issue 5. Subsequent issue 6 fixed missing structure but still failed
semantic consistency. It was not evidence that a prompt repair alone solved the pipeline.

What the evidence does not settle
Submission package complete is different from every workflow or rubric item succeeding

Hindsight
The first change would be to validate the actual role-to-tool contract before a long issue run. The available
endpoint, required JSON fields, generator output bundle and checker expectations must agree in one small
end-to-end test. This project repeatedly spent provider time discovering contract gaps only at finish. A shorter
acceptance path would have exposed missing files_changed feedback and mismatched harness tests sooner.
The second change would be to define an evaluation stop rule and artifact closeout early. Repeating
unchanged failed runs delayed the report and final evaluation without answering a new question. Finalization
now preserves terminal failures and the unanswered model-quality experiment instead of promising indefinite
retries. These reflections are AI-assisted drafts, not invented claims of unaided student reasoning.

Limitations and grading risks
- Only one corrected end-to-end issue outcome completed. Alt 4/5 were not newly corrected; historical passes and
current code may differ from the strict final contract.
- E1 did not complete a controlled model-quality comparison. Its operational failures cannot establish relative coding
quality. E2 is small, local, single-model and uses authored context with one run per condition.
- The demo shows a recovered multi-run chain rather than a single uninterrupted run. Late work after the deadline is
timestamped honestly; no extension approval is asserted.
- Token accounting is incomplete across superseded runs, provider errors and separate review increments. Requested
models differ from returned identities; no invented total cost is supplied.
- Judges can miscalibrate readiness and correlated model blind spots remain. Prefix shell checks are not a sandbox;
arbitrary Python and source-level influence remain risks.
- Substantial workflow, experiment, ADR and report work used AI assistance. The brief permits coding help but requires
reviewed output and student-owned ADR reasoning. This package does not assert unaided authorship or invent
independent student explanations.
